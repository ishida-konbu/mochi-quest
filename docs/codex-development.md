# Local-first development and Codex orchestration

This document governs engineering workflow, not game canon. The root AGENTS.md and scoped Wiki instructions remain applicable. Use the current approved roadmap and owning design pages for features and acceptance criteria.

## 1. Environment and release boundary

- Use a trusted **local** Codex project/CLI rooted in the intended worktree on the owner's computer. A cloud task is not the owner's localhost. Select Standard speed and workspace-scoped permissions; do not grant blanket network, shell or deployment permissions. Custom agent prompts are not sandbox isolation. Do not pass production secrets to the development session. Never expose save files, tokens, evidence containing private information, or unpublished plans to a public branch without approval.
- Check `git status --short`, `git branch --show-current`, `git rev-parse HEAD` and relevant changes before editing. Preserve all user changes. Create a dedicated local branch or worktree off the agreed base; never edit the production branch directly. No automatic commits if the task forbids them. No force-push, destructive reset, or cleanup of user changes.
- README's documented production pipeline is Cloudflare Workers Builds on pushes to GitHub `main`, using `npm run build` and `npx wrangler deploy`. The live Cloudflare dashboard settings are not established by repository text; verify production branch, preview build settings and commands before *any* approved remote write for a release. Never assume a non-main branch is free of preview builds. Do not push or create PRs in local implementation mode.
- Local commands (Node 22; use existing lockfile):
  1. `npm ci` when dependencies are not installed.
  2. `npm test` for baseline and regression.
  3. `npm run build` for production-like asset packaging (includes prebuild tests).
  4. `npm run dev` (predev builds, then Wrangler local). Use the actual terminal URL, normally http://localhost:8787/two/. Restart/rebuild as needed for updated bundled assets. A quick static server is not a substitute for the Worker build.
- Building may read approved missing music assets from the current public origin and verify their digests; this is not a deployment. Do not upload audio or replace the manifest to bypass a failed check. For a network-blocked build, report the missing dependency; obtain permission for read-only asset retrieval if needed.
- Serve locally only. Use disposable browser profiles/contexts and test fixtures, including copies of older saves. Never point tests at the production origin or modify the owner's actual browser storage. Inspect localStorage migration and reject invalid saves without destructive overwrite. Maintain local-only evidence outside tracked files unless explicitly approved for inclusion. Do not add production storage, new paid infrastructure or runtime inference as part of tooling.
- Build output and local Wrangler state are not source code. Do not commit dist, node_modules, credentials, or transient QA assets.

## 2. Plan, route, implement

1. Read applicable AGENTS.md, Wiki index, decisions, roadmap, architecture and acceptance criteria; follow only relevant owner pages and references. Inspect actual source, tests and baseline. Treat derived catalogs as data previews unless the approved plan says otherwise. Identify discrepancies, blocking decisions and existing work. Do not make new canon or change the user's intended scope.
2. Establish a concise task graph with prerequisites, file ownership, interface/data contracts, testable outcomes and visual references. Prefer vertical slices over giant horizontal scaffolding; each slice leaves the game playable. Build a representative high-quality reference implementation for new shared mechanics/art before scaling regional data. Do not parallelize unresolved interfaces.
3. Route by difficulty and impact, not role names alone. Initial recommendation for phase-scale orchestration: GPT-6.2 Astra High, Standard speed. For small, bounded changes select GPT-6.2 Sol Medium/High and work directly. Use the least costly model likely to satisfy the actual acceptance bar. For implementation spawn built-in workers with explicit supported model/effort as appropriate: Sol Medium for structured data and established patterns; Sol High for features, game state, UI and tests; Astra Medium/High for architecture, geometry, materials, animation, camera, physics and difficult integration. Luna High may map narrowly scoped source paths; do not use it to judge visual quality. Use Astra xhigh for genuinely hard unresolved issues; max only if warranted and available. Fixed custom agent models/effort take precedence over spawn defaults; to escalate use an appropriate separately spawned agent rather than pretending the fixed profile changed. Verify model availability in the actual local Codex client and report unavailable routing or fallback. Do not claim a model/effort was used without evidence.
4. At most three concurrently open child threads by default; close completed ones to free slots. Only the root delegates by default. Directly implement trivial tasks. Independent writers receive disjoint file ownership and stable contracts; shared integration files are owned by one agent/root. Separate worktrees for overlapping experimental implementations, or serialize edits. Reviewers do not edit production code. Never let agents concurrently mutate shared saves, builds, or browser sessions. Wait for results and integrate in dependency order.
5. Each handoff states the revision/diff, task objective, requirements/IDs, relevant paths (not the entire Wiki), constraints, writable ownership, acceptance checks and required evidence. Return a short summary of files, behavior, evidence and unresolved risks. Avoid copying whole tool logs or duplicate codebase scans. Keep a local slice checklist and resume from actual verified state after compaction or a new session.
6. Run focused automated checks and actual playable smoke tests after each slice, then full `npm test` and a clean applicable build at the milestone gate. Validate shared contracts (stable IDs, references, quantities, permissions, atomic transactions, legacy saves, cancellations and reloads). Prefer measured behavior over more speculative scaffolding. Reuse representative screenshot/clip sets across reviewers; assign each reviewer a distinct lens and allow independent probes. Escalate immediately on critical art/architecture risks instead of repeated cheap failed attempts.
7. Maintain evidence-based review and remediation following [quality review protocol](codex-quality-review.md). Preserve the established character silhouette, art direction, motion, game feel and performance. No blanket repository audit unrelated to the requested change. Do not continue into unapproved future phases.

## 3. Handoff and release

- A local milestone is ready for owner playtesting only when required checks are complete or explicitly identified as incomplete, the game is playable, material defects are fixed and rechecked, and the report distinguishes implemented vs verified vs blocked. A test pass alone is not visual acceptance. Provide the actual localhost URL, test steps (including affected keyboard/touch flows), revision and working-tree status, changed paths, screenshots/video paths, known limits, save migration notes and model/effort actually used. If available, report observed usage; do not guess token counts. Update the owning Wiki and log according to its rules.
- Owner playtests on their own Mac/browser. A separate explicit release approval must identify the reviewed revision/diff. New changes invalidate the approval for the changed scope. The release operator verifies the approved candidate, latest production base, full tests and build, actual Cloudflare build/branch settings, no secret or unintended files, and rollback readiness. If rebasing/merging changes behavior, revalidate affected scope before publishing.
- Only after that approval: commit the approved contents locally if necessary, push an approved branch/PR and merge into main according to the owner's release procedure, or use the owner's explicitly chosen release route. With the documented Git integration, merging/pushing main triggers the production build/deploy; do **not** also run `npm run deploy` for ordinary changes. Special cases such as new licensed music require the repository README's separate procedure and explicit approval.
- Confirm the Cloudflare deployment status and smoke-test the public game with a fresh profile. Record release SHA/version and the previous known-good Worker version. If a material regression occurs, halt further release changes and use the owner's approved rollback procedure; Cloudflare rollback does not restore browser saves, so migrations must remain safe and recovery copies must be retained. Keep the Git source aligned by an approved revert or fix to avoid redeploying the regression.
- Do not create a remote branch, PR, deployment or new cloud service solely to produce local evidence. Repository instructions are a policy, not a hard security barrier; actual sandbox/credentials and Cloudflare branch controls enforce separation.

## Starting a task

Example: "Implement the requested scope in the approved LLM Wiki in the current local worktree. Follow AGENTS.md and the development/quality protocols. Dynamically delegate by model and effort. Complete the requested vertical slices, run independent applicable reviews, fix and revalidate material findings, and stop at local playtest handoff. No push, PR, merge or deployment. Report in Japanese."
